Lesson 1 · C1, C4, C5, M4

localStorage is a database without the safety nets

The moment two tabs race for the same key, you discover all the durability guarantees you took for granted are missing.

What we found
  • C1 — Two scanners both read the array, both wrote a check-in flag, the second write silently wiped the first.
  • C4 — CSV import spread data.tickets directly instead of re-reading fresh storage.
  • C5 — QuotaExceededError caught, false returned, no caller cared. Check-ins appeared to succeed but never persisted.
  • M4 — One giant blob under a single key. Creating Event B overwrote Event A. No schemaVersion.
Treat storage like a tiny database
  1. Read fresh, then write. Never write based on a cached snapshot.
  2. Every write returns a result. Storage failures must surface to the UI.
  3. Plan for schema evolution from day 1 — a version field costs nothing.
  4. One key per logical entity. Two events under one key is one event.

Each fix maps 1:1 to a server concept: transactions, returned errors, migrations, table-per-entity.

Lesson 2 · C2, L5

Do the math before you pick a length

Validation hashes were 10 hex characters. Sounds plenty — until the birthday paradox shows up.

Before
return hashHex.substring(0, 10);
// 40 bits. ~0.5% collision at 10k tickets
After
return hashHex.substring(0, 16);
// 64 bits. ~10⁻⁸ collision at 10k

Entropy budget for ~1-in-10⁹ collision odds

ItemsBits neededHex chars
1 000~5013
10 000~5715
100 000~6416
1 000 000~7018
The lesson

Collision probability is n² / 2^(k+1), not n / 2^k. crypto.randomUUID() gives you 122 bits in every modern browser — free. Reach for it by default; only optimise downward when you've measured a reason.

Try it — how many items can you have?
Bits of entropy: → ~150 items at 0.5% collision risk
Lesson 3 · C3

Names are part of the contract

resetAllCheckIns() deleted every ticket. Not the check-in flags — the entire ticket array.

The mismatch
function resetAllCheckIns() {
  setData({ ...fresh, tickets: [] });  // ← deletes everything
}

UI prompt said "Reset all check-ins." Function did "Delete every ticket." The password gate above couldn't save you from that gap.

A function name is a public contract

Renaming costs five minutes. The operator who clicks it once costs a sold-out event.

When you find a name/behaviour mismatch, the answer is never "add a confirm dialog." Fix the name or fix the body.

Generalises to variable names, file names, route paths, translation keys. The closer two things look, the more dangerous it is when they diverge.

Lesson 4 · H6, H7, H8, L6

Inputs deserve four things at every boundary

Anywhere data crosses a trust boundary — paste, CSV, JSON, scanner — you owe it four checks.

1 · Shape

Is the structure what we expect? CSV header check. JSON event key check.

2 · Length cap

What's the max any reasonable input is? maxLength=100/30/30 on name/id/phone, mirrored in CSV import.

3 · Escape for next sink

Where will this data end up? CSV → Excel formula. SVG → markup. Each sink has its own escaping.

4 · Accept what's valid

/[^a-zA-Z]/ mangles non-Latin scripts. Use \p{L}\p{M} for any-script letters.

The standout: CSV injection (H8)

A buyer name =HYPERLINK("http://evil","click me") opens the link when the operator opens the export in Excel.

// Prefix any cell starting with =, +, -, @, \t, \r
if (/^[=+\-@\t\r]/.test(cell)) cell = "'" + cell;

You're not the only program that will read your output. Sanitise for the dumbest downstream consumer you can imagine.

Lesson 5 · H2, H3, M8, M9, H4

React re-render economics in a context-heavy app

Identity matters as much as value. Context is a re-render multiplier.

Before — fresh object every render
<Provider value={{ tickets, addTicket }}>
  {children}
</Provider>
// Every consumer re-renders. Always.
After — stable identity
const addTicket = useCallback(..., [deps]);
const value = useMemo(
  () => ({ tickets, addTicket }),
  [tickets, addTicket]
);
Rules of thumb
  • Any object passed down through Context must be useMemo'd.
  • Any function passed down must be useCallback'd.
  • The dep arrays must list every captured value.

The first time you skip useMemo, it doesn't bite. The hundredth time it does, you can't tell which skip caused it. Identity discipline is structural, not situational.

Lesson 6 · H5, M1, M6, M7

The real world doesn't show up in test fixtures

Time, identity, and cache are the three places where "works on my machine" diverges hardest from production.

Time — H5, M6
  • H5 — scan at any time on any day. Fix: soft confirm if outside [event ± 1d].
  • M6 — toISOString().split("T")[0] is UTC, not local. Off-by-one near midnight.
Identity — M1

QR had no eventId. A ticket from Event A scans clean at Event B if the device hasn't been wiped.

Cache — M7

Service worker rendered a stale app shell from the previous event before localStorage cleared. Whenever you see a service worker, ask: what happens after I deploy a new version?

Never hard-block the operator

At a live event, the operator is the ground truth. Events run late, VIPs arrive early, rehearsals happen. Make the software whisper, not scream — soft confirms beat hard blocks every time.

Lesson 7 · H1

Security theater is worse than no security

The "auth"
if (password !== "980827") {
  alert("Incorrect password");
  return;
}
  • Anyone with DevTools can read it.
  • Anyone can bypass it via setData(...) in the console.
  • It implies a guarantee the system can't keep.
The fix — honest friction

Replaced password with two-step "type DELETE to confirm." The confirmation is honest about what it is: friction against fat-fingering, not auth.

Be ruthless about your security model
  • If the secret ships in the JS bundle, it isn't secret.
  • If the check can be bypassed via DevTools, it isn't a check.
  • Replace fake security with honest friction.
Lesson 8 · M2, M3

Escape at the boundary, every time

Source-side escaping is fragile — new code paths bypass it. Boundary-side escaping is structural — every string crossing into the sink gets the same treatment by construction.

M2 — one field forgot
<text>{escapeXml(buyerName)}</text>
<text>{escapeXml(venue)}</text>
<text>{ticketId}</text>  // ← unescaped
M3 — dangerouslySetInnerHTML is a code smell

Sometimes necessary, never casual. Treat it as a // CONTRACT: comment that every input upstream is sanitised — and re-verify that contract whenever the upstream code changes.

The fix
  • Escape at the boundary (the place data becomes markup), not at the source.
  • Run final SVG output through DOMPurify before injecting.
Lesson 9 · L2, N1, N2, N3 + scanner pass

Route strings at the first display site

Six of 25 findings were "hardcoded English string in a Spanish app." They re-emerge because each developer types literal text inline when they're solving the real problem in front of them.

The pattern that creates the bug
<button>Update Ticket</button>     // English in JSX
{success && <p>Ready to Go!</p>}    // Same trap, success path
The rule

The moment a string is rendered, it should already be t()'d.

<button>{t("updateTicket")}</button>

Cost of doing it right: one extra import + one new key. Cost of doing it wrong: a follow-up audit pass three months later.

Edge case — short universal labels

"ID", "USD", units. Debatable. In Sígale we routed even those through t() (e.g. detailId, detailPrice) so the ES/EN switch is uniform — no half-translated screens.

Lesson 10 · L1, L3, L4, N4

The cost of "I'll come back to this"

Friction-free dev environments accumulate dead code at compound interest.

L1 — unused imports

ESLint set to warn. Bumped to error; fixed offenders.

L4 — colliding CSV shapes

Two formats (5-col, 6-col) shared one function name. Round-trip was broken. Split into ticketsToRoundTripCSV + ticketsToHumanCSV.

N4 — exports never imported

extractMimeType, purgeNavigationCache — dead. Deleted.

L3 — undocumented route

Catch-all * not in CLAUDE.md. The next dev (you, in 3 months) doesn't know it exists.

The lesson
  • Lint at error, not warn. The line between "noise" and "must-fix" is what keeps codebases honest.
  • When two artifacts share a name, they share a fate — split early, alias only with a back-compat story.
  • Document every code path — if it's not in your CLAUDE.md (or equivalent), it might as well not exist.
Cross-cutting

Designing for a future SQL migration

Throughout the remediation we kept asking: if this code has to move to a server next quarter, does the shape help or hurt?

Pattern 1 — pure-function business logic
checkInWindowStatus(event, now, windowDays)
computeStats(tickets, event)
csvToTickets(string)
generateValidationHash(ticket)

All take primitives + records, return values, no React, no storage. Each lifts to a server endpoint or stored procedure verbatim.

Pattern 2 — schema-version anchor

M4 added schemaVersion at the storage root. When you migrate, that's where the migration script branches. Without it, you're guessing which version of the data shape lives on each device.

Pattern 3 — foreign-key thinking, even without an FK

M1's eventId in the QR is a foreign key in everything but name. That's exactly what survives the migration.

The opposite pattern — write to localStorage from inside a useEffect, read from useState in three places, derive a sum in JSX — is what makes migrations hard. Pure functions don't care where state lives. UI-coupled logic does.

Cross-cutting

POC mindset vs. production paranoia

"This is a POC for ≤2 users" isn't an excuse. It's a budget.

In scope
  • Correctness — can't ship wrong data.
  • Boundary safety — CSV injection, XSS, length caps.
  • Name honesty — don't lie to the operator.
  • Basic re-render hygiene — don't ship a phone-freezer.
Deferred (not forgotten)
  • Virtualisation for 10k+ rows.
  • Multi-event storage isolation per device.
  • Bundle-split for cold-load on 4G.
  • Bulletproof cross-tab consensus.
The trick: write the condition, not the intent
Bad
// TODO: virtualise this later
Good
// H4: virtualise when ticket count
// > 5k. Acceptable per POC scope.

Without the threshold, the deferred item turns into the production incident.

Habits

Self-review checklist

Click each item as you internalise it. Good code isn't memorised — it's the questions you ask out of habit.

  • Did I read storage fresh before I write?
  • Did I memoise the context value and useCallback the actions?
  • Did I cap input length and escape for the next sink?
  • Is my function name the same shape as my function body?
  • Did the string go through t()?
  • If this had to run on a server tomorrow, would it?
  • Have I budgeted entropy of my IDs against birthday-paradox math?
  • If this is a deferral, did I write the condition, not the intent?
  • If the code touches dates, is it timezone-aware?
  • If the code uses dangerouslySetInnerHTML, is the upstream contract still true?
